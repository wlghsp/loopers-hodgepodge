## 2. Payment.createFailedPayment 개선 (권장)

**출처**: CodeRabbit Review
**우선순위**: 🟡 Medium
**파일**: `apps/commerce-api/src/main/kotlin/com/loopers/domain/payment/Payment.kt`

### 현재 문제
- `paymentMethod = PaymentMethod.POINT`로 고정됨 (생성자 기본값)
- `status`, `failureReason` 필드를 직접 수정
- 상태 전이 메서드(`markAsFailed`)를 재사용하지 않음

### 수정 방안
```kotlin
fun createFailedPayment(
    orderId: Long,
    amount: Money,
    reason: String,
    paymentMethod: PaymentMethod = PaymentMethod.CARD,
): Payment {
    return Payment(
        orderId = orderId,
        amount = amount,
        paymentMethod = paymentMethod,
    ).apply {
        // 상태 전이 규칙을 한 곳에서만 유지
        markAsFailed(reason)
    }
}
```

### 개선 효과
- 실패 결제의 결제수단을 호출 측에서 명시 가능
- 상태 전이 로직이 `markAsFailed`로 통일되어 일관성 확보
- 비즈니스 요구사항에 따라 기본값 조정 가능

## 3. 스케줄러 로직 분리 (멘토 리뷰)

**출처**: Mentor Review
**우선순위**: 🟡 Medium
**관련 파일**: 스케줄러 파일 (예상 위치 확인 필요)

### 멘토 피드백 해석
> "스케줄러에 로직을 넣지 말고, 도메인 서비스 함수호출로 처리하는게 좋아보여요. 마치 컨트롤러 처럼요."

### 의미
- 스케줄러는 **단순히 트리거 역할**만 해야 함
- 비즈니스 로직은 도메인 서비스에 위치
- 컨트롤러가 요청을 받아 서비스를 호출하듯, 스케줄러도 동일한 패턴 적용

### 수정 예시

**Before (안좋은 예)**:
```kotlin
@Scheduled(fixedDelay = 60000)
fun retryPendingPayments() {
    val pendingPayments = paymentRepository.findByStatus(PaymentStatus.PENDING)

    pendingPayments.forEach { payment ->
        try {
            // ❌ 스케줄러에 비즈니스 로직이 직접 구현됨
            val pgStrategy = pgStrategies.find { it.supports(payment.paymentMethod) }
            val result = pgStrategy?.processPayment(...)
            // ... 복잡한 로직
        } catch (e: Exception) {
            // ...
        }
    }
}
```

**After (좋은 예)**:
```kotlin
// Scheduler
@Scheduled(fixedDelay = 60000)
fun retryPendingPayments() {
    // ✅ 단순히 서비스 메서드만 호출
    paymentRetryService.retryPendingPayments()
}

// PaymentRetryService
@Service
class PaymentRetryService(
    private val paymentRepository: PaymentRepository,
    private val pgStrategies: List<PgStrategy>
) {
    fun retryPendingPayments() {
        val pendingPayments = paymentRepository.findByStatus(PaymentStatus.PENDING)
        pendingPayments.forEach { payment ->
            // 비즈니스 로직은 여기에
            retryPayment(payment)
        }
    }

    private fun retryPayment(payment: Payment) {
        // 실제 재시도 로직
    }
}
```

## 4. createFailedPayment 대신 상태 변경 함수 사용 (멘토 리뷰)

**출처**: Mentor Review
**우선순위**: 🟡 Medium
**파일**: `apps/commerce-api/src/main/kotlin/com/loopers/domain/payment/Payment.kt`

### 멘토 피드백 해석
> "createFailedPayment 같이 함수별로 만드는거 보단 Payment를 만들고 상태 변경 함수를 호출하게하도록 하는 편이 스테이트 단방향 구성의 논리적 흐름과 맞을것 같아요."

### 의미
- 특정 상태의 Payment를 직접 생성하는 팩토리 메서드보다
- **정상 객체를 생성 → 상태 전이 메서드 호출** 패턴이 더 바람직
- 상태 변경의 흐름이 명확해짐 (PENDING → FAILED)

### 수정 방안

**현재 방식** (상태별 팩토리 메서드):
```kotlin
companion object {
    fun createCardPayment(...): Payment { ... }
    fun createPendingPayment(...): Payment { ... }
    fun createFailedPayment(...): Payment { ... }  // ❌
}
```

**권장 방식** (객체 생성 + 상태 전이):
```kotlin
// 호출 코드
val payment = Payment.create(
    orderId = orderId,
    amount = amount,
    paymentMethod = PaymentMethod.CARD
)
payment.markAsFailed(reason)  // ✅ 명시적인 상태 전이
paymentRepository.save(payment)
```

### 참고
- CodeRabbit의 `createFailedPayment` 개선안과 방향이 유사함
- 두 피드백 모두 **상태 전이 메서드 재사용**을 강조
